Clockwise Theme App Development Guide

This guide covers Lua runtime API 1, CWP2 app packages, and the app metadata features introduced in firmware 0.9.3. Start with examples/hello-clock, then add assets, per-level loading, and interaction incrementally. For package details, see Theme App Format.

1. Understand the four file types

File or directoryPurposeRecommended for manual editing?
A folder containing theme.jsonApp source, including Lua, images, and data resourcesYes; this is the recommended starting point
A ZIP of the same folderA portable distribution of editable sourceExtract it before editing
.cwpAn app package installed on the device, containing runtime source, a resource directory, metadata, and an editable archiveEdit the source and repack; do not edit the binary directly
A v3 file exported by the studio: .jsonA browser project storing editor state, sprite definitions, and source codeAlso editable; different from the package manifest in theme.json

.lua files can also be imported individually, but they lack a complete package identity and device requirements declaration, so they are unsuitable for a formal release.themes/gallery/*.json contains the project sources for built-in themes. The adjacent .lua and themes/apps/*.cwp files are build outputs; changes to them will be overwritten by the next build.

2. Build your first clock in five minutes

In theme-studio, open a terminal:

powershell
npm install
npm run dev

Open the local theme studio, click “Import folder”, and choose examples/hello-clock. Themes are fixed at 64×64. Click “Run” or press Ctrl+Enter. The desktop preview uses your computer's time; its A/B buttons simulate input.

The example changes color every second and displays slowly moving stars, the time, and the date. Button A changes the color; button B hides or shows the stars. It requires no images, recorded animation, or external services.

Pack and check:

powershell
node tools/theme-app.mjs pack examples/hello-clock --out .build/hello-clock.cwp
node tools/theme-app.mjs check .build/hello-clock.cwp
node tools/theme-app.mjs check .build/hello-clock.cwp --device http://172.16.11.5

The final command only reads device capabilities and checks compatibility. It does not upload anything or switch themes. Passing a structural check does not establish that on-device memory and frame-time tests have passed.

The browser preview allows up to 256 KiB of source. Device limits still follow actual capabilities: a classic ESP32 without PSRAM commonly allows 64 KiB, while the current S3 with PSRAM allows 256 KiB. Running in the studio therefore does not mean an app can be installed on every device. The browser target frame rate supports 1..60; this example starts at 30 FPS.

In the device dashboard, open “Theme apps” → “Install app file or theme folder” and choose the generated CWP, source ZIP, or folder. Installed apps can run offline. A matching app identity updates the existing app; storage must temporarily accommodate both the old app and the new package. Export a backup of your own source before editing and publishing.

3. Recommended structure and manifest

text
hello-clock/
  theme.json
  main.lua
  README.md

For a theme with assets, expand it to:

text
my-theme/
  theme.json
  main.lua
  scripts/
    helpers.lua
    scene.lua
  assets/
    hero.json
    hero-1.png
    hero-2.png
  media/
    water.cwa
  resources/
    level-data.cwr

A minimal manifest example:

json
{
  "format": "clockwise-theme-package",
  "version": 1,
  "id": "hello-clock",
  "packageName": "org.clockwise.examples.hello-clock",
  "title": "Star Clock",
  "appVersion": "1.0.0",
  "description": "A low-memory clock with colors changing each second and slowly moving stars.",
  "author": "Your name",
  "runtimeApi": 1,
  "width": 64,
  "height": 64,
  "fps": 30,
  "entry": "main.lua",
  "scripts": [],
  "assets": [],
  "media": [],
  "resources": [],
  "data": {},
  "requirements": {
    "chips": ["esp32", "esp32s3"],
    "psramBytes": 0,
    "luaHeapBytes": 49152,
    "luaWorkingBytes": 32768,
    "graphicsBytes": 12288,
    "targetFps": 30
  }
}

version is the source package manifest format version; appVersion is your app release version; runtimeApi is the required firmware API version. These are three different concepts.packageName is a stable identity and must remain unchanged for updates. Changing the display name or version should not generate a new package name.id is retained for resource and legacy project compatibility. An installation slot number must not replace the app's identity.

requirements describes requirements declared by the author, not automatic measurements:

  • chips uses chip family names. Declare PSRAM separately; an S3 model does not necessarily have PSRAM installed.
  • psramBytes is the required number of PSRAM bytes; 0 means that the app does not require PSRAM.
  • luaHeapBytes is the required peak Lua allocation during loading, compilation, and initialization.
  • luaWorkingBytes is the required Lua allocation during sustained operation. Leave room for temporary strings and garbage collection.
  • graphicsBytes covers native graphics resources and related working memory. Do not substitute image file sizes for this value.
  • targetFps is the requested theme execution frequency. CPU work, asset decoding, and concurrent Wi-Fi activity still affect actual frame times. A lower frequency does not guarantee smooth operation.

All memory values are in bytes. Do not understate requirements to bypass checks. Initialization checks during installation cannot cover every game level or random execution path. Device compatibility and runtime performance require separate checks.

4. Lua lifecycle

A theme may define the following global functions. Undefined callbacks are skipped:

lua
function start() end
function update(dt_ms) end
function draw() end
function second() end
function minute() end
function button(key) end

Loading proceeds in this order: define sprites → execute libraries and scripts (in manifest order) → execute entry Lua → cache callbacks → start() → first draw(). Subsequent updates first check for second and minute changes, then call second(), minute(), update(dt_ms) in that order, followed by drawing. The first update also triggers the second and minute callbacks. They have not run before the first draw, so initialize cached text in start().

update receives elapsed milliseconds. Normal firmware and preview scheduling limits excessively large individual time steps, but does not guarantee exactly 16.67 ms for every frame. Move using position += speed * dt_ms / 1000 instead of calculating speed as a fixed number of pixels per frame.

Callbacks are cached at load time. Reassigning draw to another function while running does not replace the cached callback. Branch on state inside the original draw. There are no stop() / destroy() Lua callbacks. When switching or uninstalling a theme, the runtime releases that app's Lua state, sprites, layers, and animation caches.

scripts are separate Lua chunks executed in order. Each file's top-level local is visible only in that chunk. Put cross-file shared state in an explicitly named global table, such as scene = {}. The sandbox has no require(), and does not automatically register a module's top-level return value as a library.

5. Coordinates, colors, fonts, and numbers

  • The upper-left corner is (0,0); valid pixel coordinates are 0..63, with x increasing to the right and y downward.
  • Drawing colors accept RGB565 integers, such as 0xffff, or strings such as "#RRGGBB". Prefer precomputed RGB565 integers for frequent drawing.
  • gfx.text uses a small ASCII pixel font, treating lowercase as uppercase. It does not support a complete Chinese character set.font.draw("menu12",...) includes only the Chinese subset generated into the firmware. Passing arbitrary Unicode does not add missing glyphs.
  • Font IDs include mario, segment, sans, bold, italic, pixel, thin, menu12. Each font has its own glyph coverage. Numeric fonts do not necessarily include English letters.
  • Native firmware configures Lua with 32-bit integers and single-precision floating point. Browser numbers do not exactly match native precision. Large integers, long-running accumulated values, and floating-point boundaries require checks on real hardware.
  • Lua tables and sprite frames are 1-based; binary resource read offsets are 0-based.

6. Native drawing API

Every color in the following table accepts the color forms above. Functions return no value unless stated otherwise.

Off-screen content is clipped. Negative widths or heights draw nothing. Invalid colors, unknown fonts, NaN, and infinity produce errors.gfx.daylight does not calculate astronomical parameters. The script or a resource must supply solar declination and the longitude directly beneath the Sun.

7. Sprites and layers

Editable sprites

Reference JSON in the manifest:

json
"assets": ["assets/hero.json"]

assets/hero.json minimal example:

json
{
  "id": "hero",
  "width": 3,
  "height": 3,
  "palette": ["#ff4040", "#ffffff"],
  "frames": [".0.010.0."],
  "encoding": 4
}

In one-hex-digit encoding, 0..f are palette indices, and . is transparent. Every frame must contain exactly width*height pixels.encoding:8 uses two hexadecimal digits per pixel. Write transparent pixels as ..; each frame string must be width*height*2 characters long. Colors must use #RRGGBB. Frames are limited to 64×64, each sprite to 32 frames, and each theme to 16 sprites.

You can also reference PNG frames directly:

json
"assets": [
  {"id":"hero","frames":["assets/hero-1.png","assets/hero-2.png"]}
]

All PNG frames in a sprite must have the same dimensions, no larger than 64×64. Pixels with alpha below 128 become transparent; the remaining pixels may use at most 255 colors in total. The browser converts PNGs through createImageBitmap and OffscreenCanvas. The current Node CLI does not decode PNGs directly and will display conversion guidance. Import through the browser studio first, then export a source package containing sprite JSON, or preprocess your images into sprite JSON yourself.

APIDescription
sprite.draw(id,x,y,frame=1,scale=1,flip=false)Draw a sprite; frame numbers wrap, scale is 1..4; flip flips it horizontally
sprite.frames(id)Return the frame count; an unknown ID produces an error
sprite.tilemap(id,map,columns,x=0,y=0,packedRows=0)Draw visible tiles. By default, map is a hexadecimal string; 0 leaves a tile empty, and 1..f are sprite frame numbers
assets.define(id,w,h,palette,frames,digits=1)Low-level sprite definition; palette colors are comma-separated, frames are separated by |, and digits is 1 or 2. Normally generated by the packer rather than written manually
layer.save(id)Save a snapshot of the entire current screen; at most 2 cached layers, 8192 bytes each
layer.draw(id,x=0,y=0)Draw the snapshot at the specified position

A normal tilemap string length must be divisible by columns, with at most 4096 columns and 65536 bytes in the string. For packed data, set packedRows>0; map is a binary string storing one nibble per pixel, and its byte count must be ceil(columns*packedRows/2), with at most 8192 rows. Generate this data using resource.rle4(data,true).

The packer budgets 48 KiB for decoded sprite pixels. The native layer separately limits resources, including palettes, to 64 KiB. These are structural limits; low-memory themes should stay well below them. Layer caches save CPU time but consume internal memory. Redrawing a simple background is often a better choice.

Native particles

lua
function start()
  fx.create("snow", 16, 0, 0, 64, 64, 0, 4, 0xffff, "point")
end
function draw()
  gfx.clear(0)
  fx.draw("snow")
end

fx.create(id,count,x,y,w,h,vx,vy,color,style) creates a particle group. Up to 4 groups are supported, each with 1..128 particles and an area width and height of 1..64. Speeds are in pixels per second.style supports point, rain, spark; other strings use the point style.fx.draw(id) draws an existing group; the host updates positions automatically using dt. Do not recreate a group every frame. Native particle parameters use about 12 bytes each, plus group structures and allocation overhead.

8. Recorded animation and custom resources

Declare these fields in the manifest:

json
"media": [{"id":"water","path":"media/water.cwa"}],
"resources": [{"id":"levels","path":"resources/level-data.cwr"}]

media supports at most 2 files; together with resources, the total is at most 8 files. Resource IDs are at most 31 ASCII characters, using only letters, digits, and _, -. For animation IDs, use lowercase letters, digits, and - to satisfy browser validation as well.

APIReturn value / effect
media.draw(id,x=0,y=0,ms=clock.millis())Draw CWA using the native animation decoder, without pixel-by-pixel decoding in Lua
media.release(id)Release the animation's runtime decoder cache; it can be loaded again later
resource.size(id)Return the raw resource size in bytes; a missing resource produces an error
resource.read(id,offset,count)Read a binary Lua string; offsets are 0-based, each read is limited to 8192 bytes, and out-of-bounds reads are prohibited
resource.rle4(data,packed=false)For each input byte, the high 4 bits store repeat count minus one and the low 4 bits store the tile value. Output is limited to 8192 tile values. Normal mode returns a 0123456789abcdef string; packed mode returns nibble-packed data
memory.collect()Fully collect unused Lua objects and return the current Lua allocation in bytes; this excludes native graphics memory

Animation timestamps range from 0..4294967295 and wrap by the file's total duration. CWA supports only 64×64, up to 256 frames, and a keyframe every 16 frames. Prefer indexed CWA2: native drawing can use a 4096-byte indexed frame cache plus the palette; a CWA1 RGB565 frame cache uses 8192 bytes. Streaming also requires a frame index table (16 bytes per frame) and a 512-byte read buffer. For the actual total, see on-device graphicsBytes.

.cwr is an arbitrary binary resource container without a mandatory level protocol. The script and data must agree on versions, offsets, and encoding. Large maps should have a small index and be read by level or region; do not decompress an entire world into Lua tables.

lua
local segment
local function loadSegment(offset, bytes)
  segment = nil
  memory.collect() -- Only at explicit boundaries, such as scene changes
  local compressed = resource.read("levels", offset, bytes)
  segment = resource.rle4(compressed, true)
end

resource.read returns a new string, not a zero-copy reference. Reading 8 KiB and slicing it every frame causes repeated allocation. Reuse a segment throughout a scene and release it when changing scenes.media.release releases only the corresponding decoder; it does not promise to clear firmware PSRAM caches for the whole package's resources.

9. Time, randomness, data, and input

APIDescription
clock.format(format)Supports %H, %M, %S, %d, %m; this is not a complete strftime implementation. Unsupported sequences are preserved verbatim
clock.value(field)Local time fields: hour/minute/second/day/month/year/weekday/millisecond; weekday=0 is Sunday
clock.utc(field)UTC fields: hour/minute/second/day/month/year/weekday/yearday; yearday starts at 1
clock.millis()Accumulated update milliseconds since theme loading. Native 32-bit timing has long-running boundaries; maintain a bounded phase for periodic animation
rng.seed(seed)Set the xorshift32 seed; the argument must be an integer in the uint32 range. Zero uses a fixed nonzero fallback
rng.int(lo,hi)Random integer in an inclusive interval; arguments are rounded down, with a maximum span of 1000000
rng.float()[0,1) random number
data.get(key,fallback)Read host-cached data without network access; return fallback, which may be nil, if the key does not exist
input.pressed(key)Query the current button state; the current device host recognizes A, B
telemetry.set(key,value)Submit debug state: number, string, or boolean. Do not use this as a persistence interface

The host generates the default random seed. A fixed seed supports reproducibility, but identical sequences also require the same number of calls. Use rng instead of math.random for the closest match between desktop and firmware behavior.

Temperature and humidity example:

lua
local temperature = data.get("temperature", nil)
if temperature then
  -- Generate cached text in second(), rather than formatting every frame.
end

The current board host supplies valid temperature and humidity only when supported sensors are connected. Show -- when no reading is available; do not present a default 22°C as a measurement.theme.json.data currently supplies sample data for the desktop preview. It is not arbitrary persistent configuration that is automatically written to the ESP32. The native host's current message is fixed sample text. Weather services, arbitrary user configuration, and network data sources require additional host interfaces.

The browser debug panel can display arbitrary telemetry keys. The current ESP32 status interface only aggregates connected numeric metrics such as level/area/deaths/coins. Arbitrary string keys do not automatically appear in the dashboard. Input is also limited by hardware and firmware mappings. Declaring A/B callbacks does not mean physical buttons are connected to the board.

10. Native pathfinding and optional Lua helpers

lua
local distances = nav.bfs(3, 3, ".........", 1, true)
local d = nav.at(distances, 9)
  • nav.bfs(w,h,map,start,packed=false): unweighted four-neighbor distances, up to 256 cells; # denotes a wall. The map byte count must equal w*h, and the starting cell is 1-based.
  • nav.solve(w,h,map,start,costs,packed=false): return three results: distances, first steps, and parent nodes. costs is a Lua array; the default cost is 1, and integer costs from 0..1000000 are allowed.
  • Normal mode returns tables with nil for unreachable cells. Packed mode returns compact binary strings; read them using nav.at(result,index) instead of indexing them as Lua arrays.
  • nav.at(result,index): return the cell value, or nil if unreachable. The encoding header determines the data width; do not substitute unrelated strings.

util is not a native firmware global library. If needed, copy themes/lib/core.lua into scripts/core.lua in your own directory and add it to the manifest's scripts:

json
"scripts": ["scripts/core.lua", "scripts/scene.lua"]

This library provides util.clamp(v,lo,hi), util.lerp(a,b,t), util.wave(ms,period,lo,hi), util.frame(ms,fps,count), util.every(id,interval).every only registers a timer and returns false on its first call; it does not trigger immediately. Calls with the same ID share a timer.

11. Writing for low-memory devices

On a classic ESP32 without PSRAM, firmware must allocate memory for DMA scanning, Wi-Fi, HTTP, Lua, and native graphics while contending with contiguous-block fragmentation. Source size, CWP file size, and actual Lua allocation are three different quantities.

PreferAvoid
Create fixed-size tables in start and update their numbers in updateCreating tables, concatenating strings, or formatting time every frame
Cache text in second/minuteRepeated clock.format / string.format calls in draw
Native font, sprite, tilemap, and particle APIsLarge, complex images drawn with per-pixel Lua loops
Compact strings/binary data for each level or regionExpanding all 32 levels into nested Lua objects at once
Small indexed-color sprites; open animations only when neededCaching multiple full-screen backgrounds, animations, and map copies at once
Drop references after a phase and collect at transition boundariesForcing full GC every frame or retaining unused objects indefinitely
Clip to the visible region and update only changed stateWhole-map pathfinding or frequent resource reads every frame

Each layer uses 8 KiB; two use 16 KiB. Native position and parameter storage uses about 12 bytes per particle. These are not all included in Lua memory statistics. PSRAM permits larger resource caches and Lua heaps, but does not make a 240 MHz CPU faster. Themes needing substantial memory should explicitly require PSRAM; smooth desktop playback does not justify marking them suitable for every device.

Start with 30 FPS and a small asset set, then decide whether 60 FPS is necessary. The approximate total time budget per frame is 1000 / FPS milliseconds: about 16.67 ms at 60 FPS and 33.33 ms at 30 FPS. Device performance metrics computeUs, dmaUs, maxUs, late, missed help distinguish computation, frame submission, peak duration, and scheduling problems. Compare counter deltas for the same theme over the same interval. Misses caused by theme switching or upload pauses should not be directly attributed to the animation.

Firmware 0.9.3 uses the CWP2 target frequency to schedule theme execution. This does not change the HUB75 DMA scan refresh rate or guarantee that every frame finishes on time. Fengari uses JavaScript objects and a different allocator; its browser heap usage cannot be converted into ESP32 Lua byte usage.

Declared requirements provide pre-installation screening only. Before publishing, test initialization, scene changes, the most complex scene, random actions, and operation with the dashboard open on the target hardware. Record versions, peak/steady Lua allocation, graphics usage, minimum free internal memory, maximum frame time, and observation duration. Without these measurements, mark the app unverified rather than claiming “zero dropped frames” or “works on every ESP32”.

12. Common errors and fixes

Unknown font / Unknown spriteCheck IDs and case, whether the manifest includes the assets, and whether the font is actually compiled into the firmware

13. Sandbox, publishing, and updates

Firmware exposes Lua base functions, math, table, string, and the host APIs in this guide. The following are unavailable to themes: io/os/package/debug, file access, networking, GPIO, dofile/loadfile/load/require, collectgarbage/pcall/xpcall/print. Use the dedicated APIs for time and garbage collection. Themes cannot download data, write NVS, or change system settings themselves.

Keep the source folder and version history. Increment appVersion for each release and preserve packageName. Firmware may still use numeric slots to store schedules internally. App authors and user operations should prefer stable package names; slot numbers are not guaranteed to match across devices.

To migrate a legacy theme, retain its Lua and resources, add metadata and realistic requirements to theme.json, and repack as CWP2. Legacy CWP1 or standalone Lua remain compatible inputs, but cannot be assumed compatibility-certified without complete declarations. New package formats and older firmware differ in support, so confirm CWP2 support before updating. Export source for editing; export an app for a deployment backup. Do not manually change offsets in a binary app.

These interfaces cover 64×64 animated clocks, layered sprites, maps, particles, and themes with segmented data. They are not a general desktop application system and do not provide unrestricted networking, arbitrary Chinese fonts, permission management, or arbitrary user configuration storage. Add explicit host APIs and a runtime API version when introducing such capabilities, then implement consistent behavior in the browser and firmware.

Clockwise Source Packages and CWP App Format

For a development introduction, see Theme App Development Guide. This document is for packer, firmware, and tool authors. Theme authors should normally edit source folders rather than write CWP binaries manually.

1. Responsibilities of the three layers

  1. Source package: a folder/ZIP with a root theme.json manifest, scripts, and editable assets.
  2. Installation package: CWP2 stores small, directly readable app metadata, bundled Lua, a resource directory, and an editable archive. Firmware does not need to extract the entire ZIP just to read the package name.
  3. Runtime: Lua API 1 plus the native graphics engine. It reads resources on demand and checks app declarations against actual device capabilities.

packageName is a stable identity across devices; title is the display name; appVersion is the release version. Firmware may retain numeric installation slots for internal files and existing schedules, but users must not assume that the same package occupies the same slot on different devices. Run, uninstall, and export by package name to avoid acting on the wrong app or changing identity during updates.

2. Source manifest

The root manifest format is clockwise-theme-package, version:1, fixed at width:64,height:64.

FieldMeaning
idLegacy project/resource compatibility ID; retain it for new apps too
packageNameStable, namespaced app identity, for example org.example.clock.stars
titleThe name shown to users
appVersionApp version, for example 1.0.0; separate from the format version
description / authorDescription and author; these are not proof of origin or copyright permission
runtimeApiRequested theme runtime API version; currently 1
fpsTarget frame rate of the source project
entryRelative path to the entry Lua file; defaults to main.lua
scriptsRelative paths to other Lua files, executed in order; at most 32
assetsSprite JSON paths, or {id,frames:[PNG paths...]}
media{id,path} animation files; at most 2
resources{id,path} arbitrary binary data files; at most 8 combined with media
dataSample data for browser preview; currently not arbitrary device configuration storage
requirementsRequirements for chip, PSRAM, Lua loading/running, native graphics memory, and target frame rate

Identity and metadata limits:

  • packageName is limited to 63 UTF-8 bytes and accepts only lowercase ASCII namespaces: ^[a-z][a-z0-9-]*(?:\.[a-z][a-z0-9-]*)+$.
  • id is limited to 32 ASCII characters: ^[a-zA-Z0-9_-]{1,32}$.
  • appVersion is a semantic version, such as 1.0.0, with at most 31 UTF-8 bytes.
  • title is limited to 96 UTF-8 bytes, description to 384 bytes, and author to 64 bytes. Chinese characters normally use 3 bytes each; do not treat byte counts as character counts.
  • runtimeApi is a positive integer; the current default is 1.
  • requirements.targetFps is an integer from 1..60 and must match the manifest's fps. Import/export synchronizes the project value with the target frequency in requirements.

Generated CWP2 metadata also includes requirementsDeclared and verification:{"status":"unverified"}. Zero PSRAM is valid. A complete requirements declaration needs positive values for Lua loading, Lua working memory, and graphics. A zero memory value means unknown, not that the app uses no memory. PSRAM comparisons round the device-reported amount up to MiB, avoiding rejection when an 8 MiB chip's usable heap is slightly below its nominal capacity due to management overhead.

All paths are relative to the directory containing theme.json. Absolute paths, backslashes, empty path segments, . or .. are prohibited. A ZIP may have one common directory prefix, but must resolve to exactly one theme.json. The limit is 300 files. Compressed and decompressed sizes are checked against import quotas for the target device's capabilities. Importing and packing also check actual bundled source, archive, and total package sizes.

The packer converts sprite definitions into assets.define Lua chunks. Libraries and modules are concatenated in their original order, preserving execution order across files. Bundled source uses reserved markers:

text
-- @cw-bundle 1
...first chunk...
-- @cw-part
...next chunk...

Author source must not include the complete reserved separator markers. Firmware reads and compiles chunks separately, reclaiming temporary objects to avoid retaining all sprite literals and compiler temporaries at once. Chunking does not eliminate the memory consumed by permanent Lua objects or native sprites.

3. CWP2 binary layout

All integers are unsigned and little-endian. Package contents follow the table consecutively, with no implicit alignment or gaps.

File offsetLengthContents
04ASCII CWP2
44sourceSize: runtime Lua byte count
84archiveSize: editable ZIP byte count
124resourceCount: resource directory entry count, 0..8
164metadataSize: UTF-8 metadata JSON byte count, at most 2048
204flags: 0 in this version; unknown flags must not be silently interpreted
24resourceCount * 40Resource directory
Immediately after the directorymetadataSizeMetadata JSON, without a terminating NUL
Immediately after metadatasourceSizeBundled Lua UTF-8 source
Immediately after sourcearchiveSizeOriginal editable ZIP archive
Immediately after the archiveSum of resource sizesAll resources, in directory order

Each resource directory entry is 40 bytes:

Offset within entryLengthContents
032ID: ASCII, at most 31 bytes, NUL-terminated and zero-padded
324Absolute resource offset within the entire CWP file
364Resource byte count; must be greater than 0

Metadata fields are packageName/id/title/appVersion/description/author/runtimeApi/requirements/requirementsDeclared/verification. Firmware must read identity from package metadata; independently submitted titles/package names in upload URLs must not override the real identity. Resource IDs must be unique. Every offset must equal the end of the preceding content, and the last resource must end exactly at the file length. Check addition overflow, truncation, overlap, and trailing bytes.

Example calculations:

text
metadataOffset = 24 + resourceCount * 40
sourceOffset   = metadataOffset + metadataSize
archiveOffset  = sourceOffset + sourceSize
resource0Offset = archiveOffset + archiveSize

Maximum file size depends on device capabilities and storage partitions, not just the chip name. A device without PSRAM may still lack enough contiguous internal memory to run a small, structurally valid package. Devices with PSRAM must still reserve internal memory for DMA and Wi-Fi.

4. Legacy package compatibility

The first 16 bytes of CWP1 are CWP1/sourceSize/archiveSize/resourceCount, followed by the same 40-byte resource directory entries, Lua, ZIP, and resources. There is no separate metadata segment.

Legacy CWP1/standalone Lua remain compatible inputs, but compatibility should be unknown or undeclared when complete app requirements are missing; this is not device performance certification. Upgrade by adding manifest fields in the editable ZIP or source folder and repacking as CWP2. Firmware that recognizes only CWP1 cannot install CWP2; runtimeApi:1 does not mean older firmware recognizes the new binary container.

Keeping both ZIP and runtime resources in CWP can duplicate assets: the ZIP preserves editable originals, while resources at the end provide runtime data that firmware can locate directly. This mainly consumes Flash and does not mean the ZIP is extracted to RAM at runtime. On devices with limited storage, reduce archived assets, recorded animation duration, and duplicate resources rather than corrupting the format by deleting arbitrary bytes. Current flags:0 does not represent “omit the archive”.

5. CWA1 / CWA2 animation formats

Animations are fixed at 64×64. All multibyte values are little-endian.

16-byte header:

OffsetTypeContents
04 bytesCWA1 or CWA2
4u16width=64
6u16height=64
8u16Frame count, 1..256
10u16CWA2 palette color count, 1..256; CWA1 does not interpret this field as a palette count
12u32Total clip duration in milliseconds; must be greater than 0

The header is followed by an index of frameCount * 16 bytes. Each entry contains four u32 values in order: data offset relative to the frame data area, data byte count, cumulative milliseconds at the end of this frame, and a keyframe flag of 0 or 1. End times must increase strictly; the final end time must equal total duration. Frames 0, 16, 32, … must be keyframes. Encoded data for one frame must not exceed 16384 bytes.

After the CWA2 index comes an RGB565 palette of colorCount * 2 bytes, followed by the frame data area. CWA1 proceeds directly to frame data. Each frame operation begins with a u16: the low 14 bits encode length n, which must be positive, and the upper two bits specify the operation.

Upper bitsOperation
0x0000Literal: followed by n color values
0x4000Repeat: followed by one color value, repeated n times
0x8000Keep the corresponding n pixels from the previous frame, with no following color value; prohibited in keyframes
0xc000Invalid

CWA1 color values are 2-byte RGB565; CWA2 uses 1-byte palette indices. Operations in each frame must cover exactly 4096 pixels without exceeding bounds. Seeking decodes from the keyframe in the same group, going back at most 15 frames. File frame rate and display refresh rate are different concepts.

The firmware drawing path can use a CWA2 indexed frame and palette directly, avoiding an always-allocated RGB565 conversion frame. Caches are allocated only when used. Release a decoder with media.release. Desktop preview and device memory implementations differ; browser object sizes do not measure device memory usage.

6. CWR and tile data

.cwr is author-defined binary data with no universal header or compression algorithm. A small custom header is recommended: magic, version, entry count, and each entry's offset/size. Read the index first in Lua, then load content by level or region.

Native resource.rle4 uses this single-byte encoding: (repeatCount - 1)<<4 | tileId, with repeat count 1..16 and tile ID 0..15. Normal mode returns hexadecimal characters. Packed mode stores two tile values per byte, low nibble first and then high nibble. Decoded output is limited to 8192 tiles.

A normal tilemap string uses 0 for an empty tile, and 1..f for sprite frames 1..15. For packed data, specify the row count with packedRows. RLE data does not automatically implement collisions, pathfinding, enemy behavior, or level changes; the theme Lua handles these.

7. Compatibility and performance declarations

Pre-installation screening should separately check at least container structure/size, runtime API, chip family, PSRAM, Lua load quota, Lua working quota, native graphics requirements, and actual free storage. Allocation failures must still be observed during real initialization; declarations do not replace the allocator.

compatible only means that declared static requirements do not exceed current device capabilities; unverified means performance validation on the target device is incomplete. Measurement records should include app package name/version, firmware version, chip and PSRAM, observation duration, covered scenes, peak and steady Lua allocation, native graphics usage, frame times, and dropped-frame counter deltas. An author's target FPS, memory estimates, or “tested” label do not automatically certify a device.

The worst case across all 32 game levels may not occur on the title screen. Installation runs initialization and the first frame only; this cannot guarantee smooth behavior in every scene. Report desktop structural checks, Fengari preview, native initialization, and long-running scene tests on hardware separately.

8. Manage apps by stable identity

Firmware supporting the new app interfaces provides:

RequestParameters
GET /api/appsReturn installed entries, metadata, compatibility status, device capabilities, and remaining storage
POST /api/apps/installUpload CWP as multipart data; package metadata determines identity and the update location or available slot
POST /api/apps/runForm: packageName=org.example.clock
POST /api/apps/uninstallForm: packageName=org.example.clock
GET /api/apps/export?packageName=org.example.clockExport the installed package

HTTP forms also accept legacy id; numeric index remains for compatible callers. New clients should prefer packageName. An upload URL may include a package name to express intent, but cannot override the metadata inside CWP2.

PowerShell example for running an app:

powershell
Invoke-RestMethod -Method Post -Uri 'http://172.16.11.5/api/apps/run' `
  -ContentType 'application/x-www-form-urlencoded' `
  -Body @{ packageName = 'org.clockwise.examples.hello-clock' }

To uninstall the same app, change the URL suffix from run to uninstall. Uninstalling the active theme returns to the basic clock and clears its associated schedules. Users should target their own installed app when executing this command.

Serial commands use one JSON object per line at 115200 baud:

json
{"cmd":"apps"}
{"cmd":"app.run","packageName":"org.clockwise.examples.hello-clock"}
{"cmd":"app.uninstall","packageName":"org.clockwise.examples.hello-clock"}

id and legacy index remain for compatibility, but release documentation must not treat a particular slot number as an app's stable identity.
